Design a synthesizable digital IP block for an automotive active-aerodynamics controller. The physics surrogate itself is external and shall not be implemented in RTL. The IP shall provide a request/response gateway for the NVIDIA DoMINO Automotive Aero model, using the supplied model interface only. The RTL shall be clocked and reset synchronously with a single system clock domain unless otherwise integrated through a standard CDC wrapper.

1. Top-level function
- Accept vehicle_geometry metadata/payload descriptor and flow_conditions inputs.
- Form model request transactions containing at minimum: sequence_id, timestamp, geometry descriptor, and flow condition data.
- Interface to an external model runtime through a bidirectional request/response channel compatible with future NVIDIA-hosted NIM or ChipLoop GPU worker deployment.
- Consume model outputs: drag_force, lift_force, surface_pressure, and flow_field.
- Generate a bounded actuator_command for active aerodynamic hardware.

2. Interface behavior
- Inputs shall include valid/ready handshake or equivalent request acceptance signaling.
- The module shall assign monotonically increasing sequence_id values to each accepted request.
- The module shall store the last accepted request timestamp and compare each response age against a programmable timeout threshold.
- The module shall treat any response with mismatched sequence_id, missing fields, invalid framing, or timeout exceedance as invalid.
- The module shall reject stale model commands by blocking them from the actuator path and asserting a stale_reject status.

3. Safety state machine
- Implement states: IDLE, REQUEST_SENT, WAIT_RESPONSE, VALIDATE_RESPONSE, COMPUTE_CONTROL, APPLY_CLAMP, Fallback, FAULT_LATCH.
- On reset, enter IDLE and safe fallback output.
- On request acceptance, move to REQUEST_SENT then WAIT_RESPONSE.
- On valid response, move to VALIDATE_RESPONSE and then COMPUTE_CONTROL.
- If validation fails, timeout occurs, communication error occurs, or input envelope is violated, transition to Fallback.
- Fallback shall drive a deterministic safe actuator command defined by a configurable safe_state value and shall assert fallback_active.
- Faults shall latch in FAULT_LATCH until clear_fault is asserted or reset is applied, depending on integration policy.

4. Command generation and clamping
- The control path shall accept validated aerodynamic outputs and translate them into a command word for the active-aero actuator domain.
- The output command shall be constrained by cmd_min and cmd_max registers or parameters.
- A combinational clamp stage shall ensure cmd_out = min(max(cmd_in, cmd_min), cmd_max).
- The final actuator output shall only be asserted when the response is valid and fresh, or when fallback is active.
- No unvalidated model data may reach the actuator output.

5. Envelope and configuration handling
- The architecture shall support the specified stream_velocity_mps operating envelope of 20 to 55 m/s.
- A programmable guard shall flag any stream_velocity_mps value outside the envelope as out_of_range and force fallback or fault handling.
- Reference-condition metadata shall support stream_velocity_mps = 38.89, geometry_format = STL, and geometry_source = DrivAerML reference geometry as a configuration context only.
- The RTL shall not parse or simulate the geometry physically; it shall only carry, tag, and transmit geometry descriptors or payload references as required by the external model interface.

6. Diagnostics and registers
- Provide status registers for model_online, timeout, stale_reject, fallback_active, fault_latched, and last_sequence_id.
- Provide control registers for timeout threshold, cmd_min, cmd_max, safe_state, clear_fault, and enable.
- Provide readback of current FSM state and the most recent accepted response metadata.

7. Timing and synthesis constraints
- All outputs shall be registered except pure clamp combinational logic between registered stages.
- The design shall be fully synthesizable in standard-cell ASIC flow.
- No floating-point arithmetic is required in RTL unless explicitly implemented as fixed-point conversion logic around the command mapping stage.
- If fixed-point arithmetic is used, it shall be parameterizable in width and fractional bits, with saturation behavior on overflow.
- The block shall be deterministic, with no dependence on external software scheduling for safety outcomes.

8. Verification-oriented requirements embedded in RTL intent
- Assert that stale responses never reach actuator_command.
- Assert that actuator_command always remains within [cmd_min, cmd_max].
- Assert that invalid or missing responses force fallback within one control cycle or less, subject to the configured latency budget.
- Assert that a latched fault prevents nominal command emission until cleared.
- Assert that out-of-envelope stream velocity forces a safe response.
