The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, fallback, and bounded actuator-command behavior.
Module name: adaptive_aero_control_top.

This module shall be synthesizable FPGA RTL and shall NOT implement the NVIDIA DoMINO surrogate model. The module shall implement a hardware control wrapper that exchanges compact request/response transactions with an external software/GPU surrogate service and drives active-aerodynamics actuator commands with validation and safety enforcement.

Top-level interface requirements:
1) Provide one outbound streaming request interface req_valid/req_ready/req_data[127:0].
2) Provide one inbound streaming response interface rsp_valid/rsp_ready/rsp_data[127:0].
3) Provide a compact control/status register window with address/data semantics using no more than 64 bits of register-window addressing/transport per transaction, suitable for configuration of enable, timeout, velocity setpoint, command clamp bounds, and status reads.
4) Provide one compact actuator command output act_cmd_valid/act_cmd_data[31:0].
5) Provide one fault/status output fault_valid/fault_code/fault_flags.
6) Do not expose tensors, flow fields, surface pressure grids, or geometry arrays as top-level pins.

Internal architecture requirements:
1) Control register file:
   - Implement registers for global enable, soft reset, mode select, request sequence number, last accepted sequence number, stream_velocity_mps setpoint, response timeout threshold, actuator min/max clamp values, and safe-fallback selection.
   - Reset state shall place the controller in safe fallback with actuator commands deasserted or set to a conservative default.

2) Request packetizer:
   - Construct 128-bit requests containing at minimum: transaction sequence ID, control mode, compact geometry descriptor or reference token, encoded stream velocity or scaled flow-condition field, and request validity markers.
   - The geometry source is the DrivAerML reference geometry in STL form; however, RTL shall carry only a bounded descriptor, ID, or hash/reference, not the raw STL.
   - Requests shall only be emitted when enabled, when downstream transport is ready, and when no blocking fault is active.

3) Response depacketizer:
   - Accept 128-bit responses and extract compact control-relevant outputs such as drag estimate, lift estimate, response sequence ID, validity, and freshness metadata.
   - The module shall not require the full surface_pressure or flow_field payload to compute actuator command decisions in hardware.
   - Any response failing header/format checks shall be rejected.

4) Sequence and freshness monitor:
   - Track outstanding request sequence IDs.
   - Reject stale responses, replayed responses, duplicate responses, and responses that do not match the outstanding request.
   - Maintain age counters and compare against the configured timeout threshold.
   - Assert stale-response and timeout fault flags when conditions are violated.

5) Safety supervisor:
   - Validate model outputs against configured bounds and known-safe operating envelope.
   - Clamp actuator intents to min/max limits.
   - If any response is invalid, stale, late, missing, or indicates malformed data, assert safe fallback and suppress normal command issuance.
   - Safe fallback shall produce a deterministic conservative command or hold-last-safe command according to configuration.

6) Actuator command shaper:
   - Convert validated control intent into a compact 32-bit actuator command word.
   - Implement rate limiting or slew control if needed for safe actuator behavior.
   - Ensure command output remains within the configured clamp range.

7) Timeout watchdog:
   - Count cycles or timebase ticks from request issuance until valid response acceptance.
   - Force fallback when no valid response arrives before timeout.

8) Telemetry/status:
   - Expose sticky fault bits for stale response, timeout, invalid payload, clamp event, fallback active, and disable state.
   - Provide a readable status word for host software.

9) Clock/reset behavior:
   - All sequential logic shall use a single primary clock and synchronous or safely synchronized reset strategy.
   - On reset, clear outstanding transaction state, invalidate pending responses, and enter safe fallback.

10) Implementation constraints:
   - The design shall be FPGA-friendly and use standard RTL constructs only.
   - No ASIC hard macros, no inferred bulk payload memories, no register-array FIFOs for model payloads, and no exposure of surrogate internals.
   - All bulk physics computation remains external to the RTL; the hardware only manages transport, validation, safety, and command generation.

Functional intent:
- At stream velocities within 20 to 55 m/s, using the specified reference geometry and operating point of 38.89 m/s, the hardware shall request surrogate evaluation and use accepted outputs to produce safe active-aerodynamic commands.
- The design shall prioritize deterministic safety behavior over aggressive control, given the architecture-only evidence and absence of executed inference results.

FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
