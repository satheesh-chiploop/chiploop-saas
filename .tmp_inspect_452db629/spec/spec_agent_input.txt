Implement top module adaptive_aero_control_top as a synthesizable FPGA digital IP wrapper for an intelligent active-aerodynamics controller. The module shall not implement the NVIDIA DoMINO surrogate model itself. Instead, it shall provide control-plane logic for requesting surrogate evaluation from external software/GPU infrastructure, receiving bounded responses, validating those responses, and converting them into safe actuator commands.

Top-level implementation constraints:
1) The top module shall use a compact implementation-friendly interface. Do not expose vehicle_geometry, flow_fields, surface_pressure arrays, or any surrogate tensor payload as top-level pins.
2) Use a bounded streaming request/response interface with valid/ready handshake. Payload width shall be no greater than 128 bits per transfer.
3) Use a Wishbone memory-mapped register interface for CPU-visible control/status registers. If a register window is used, it shall be no wider than 64 bits per addressable data path segment.
4) The design target is FPGA; do not instantiate Sky130 hard macros or ASIC SRAM macros.
5) All bulk model payload storage shall remain external to RTL or in FPGA BRAM-backed buffering only, never as large reg arrays on the top level.

Functional blocks:
A) Control/status CSR block: provide registers for enable, mode select, request sequence number, timeout threshold, clamp min/max, fallback mode, and fault status. Registers shall be 32-bit accessible via Wishbone.
B) Request packetizer: on CPU command, package a bounded request frame containing request_id, geometry descriptor handles, flow-condition scalar values, model_version, and checksum/CRC. The frame shall be emitted on model_req_stream with valid asserted until ready or until canceled by safety logic.
C) Response depacketizer: accept model_rsp_stream frames, verify matching request_id, verify model_version, verify checksum/CRC if present, and update response_valid only if all checks pass.
D) Stale-data monitor: maintain an age counter from request issue to response acceptance. If age exceeds timeout threshold, assert timeout_fault and discard the response.
E) Safety monitor: combine timeout_fault, invalid_response, CPU_disable, and external_fault into a single safe_fallback request. Safety logic shall have priority over normal command generation.
F) Actuator clamp unit: clamp commanded values to configured safe bounds. If a rate-limit mode is implemented, clamp rate of change as well as absolute position.
G) Safe fallback controller: when any fault is active or enable is deasserted, drive actuators to a predetermined safe position or hold-last-safe position, as specified by configuration.
H) Interrupt generation: generate a single-cycle interrupt to the soft CPU when a valid response is accepted, when a timeout occurs, or when a fault state changes.

Data format requirements:
- Request stream payload example fields: request_id, operation_mode, stream_velocity_mps, geometry_handle, geometry_crc, reference_geometry_id, model_version, reserved. The exact bit allocation shall be implementation-defined but total payload width shall not exceed 128 bits.
- Response stream payload example fields: request_id, drag_force_est, lift_force_est, status_flags, model_version, reserved. Total payload width shall not exceed 128 bits.
- Actuator command outputs shall be discrete or fixed-point signals for the active-aerodynamics surfaces, with explicit clamping logic and safe defaults.

State machine requirements:
- IDLE: wait for enable and CPU request.
- ISSUE_REQUEST: emit request frame and start timeout counter.
- WAIT_RESPONSE: wait for ready/valid response or timeout.
- VALIDATE_RESPONSE: check request_id, version, and integrity.
- APPLY_CONTROL: update actuator target after passing validation and clamp.
- FALLBACK: override outputs to safe state until fault clears and a new valid command is issued.

Timing and robustness:
- The design shall tolerate CPU stalls and external model-service stalls.
- A response arriving after timeout shall be rejected and shall not update actuator targets.
- Duplicate responses for an already consumed request_id shall be rejected.
- Any malformed frame shall set invalid_response and transition to FALLBACK.

Memory and buffering:
- Only small control/status registers, sequence counters, timers, and FSM state may be stored in flip-flops.
- If any response/request staging buffer is required on FPGA, it shall use the vendor FPGA BRAM abstraction in the integration layer; the top-level RTL shall not hardcode a specific vendor primitive.
- No inferred ASIC SRAM, no generic payload SRAM for ASIC, and no large register-array payload storage.

Safety behavior:
- Default reset state shall be safe fallback with actuators deasserted or set to safe positions.
- Clamp limits shall be programmable but constrained by hard-coded safety bounds in RTL.
- A watchdog shall assert fallback if the CPU does not refresh enable or if model service does not respond within the configured window.
- Safety outputs shall be monotonic in priority: fallback overrides clamp overrides nominal command update.

Implementation notes for Arch2RTL:
- Generate synthesizable RTL for the control wrapper, register bank, packetizer/depacketizer, watchdog, and clamp logic only.
- Treat the surrogate as an external service accessed through the bounded stream interface or host software running on the soft CPU.
- Verify that top-level I/O count remains below 256 scalar-equivalent pins.
