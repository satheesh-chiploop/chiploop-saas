The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, and bounded actuator-command behavior.

The RTL receives model-response valid/data as inputs and emits model-response ready as an output. Apply this rule by data flow even when application-specific ports use cmd_*, req_*, rsp_*, or response_* names. A top-level output must have a real RTL driver; never connect a required top-level output only to a child input.

Module name: adaptive_aero_control_top.

Implement a synthesizable FPGA RTL wrapper for an external intelligent active-aerodynamics controller. The RTL shall not implement the NVIDIA DoMINO surrogate model or any physics solver. Instead, it shall provide request/response transport, buffering, validation, timeout control, stale-data rejection, actuator command shaping, and safe fallback.

Top-level ports shall be compact and implementation-friendly. Use a single clk and rst_n. Provide a 64-bit control/status register window or equivalent compact register interface for configuration and readback. Provide a bounded host request channel and bounded host response channel using valid/ready handshakes; each data bus shall be no wider than 128 bits. Do not expose tensors, geometry arrays, flow fields, or a large number of pins at top level. Total scalar-equivalent I/O shall remain below 256.

Functional requirements:
1) Control/status registers shall include at minimum: enable, arm, clear_faults, request_sequence, response_sequence, timeout_threshold, clamp_min, clamp_max, fallback_mode, and status bits for busy, valid_response, stale_data, timeout, invalid_response, and fallback_active.
2) On reset, outputs shall enter safe fallback state and fault flags shall clear to a deterministic reset value.
3) When enabled and armed, the module shall accept compact descriptors from the control plane, form a request frame, and issue host_req_valid with host_req_data. The request frame shall contain only compact metadata such as sequence ID, operating-point ID, velocity setpoint, geometry descriptor hash or handle, and flow-condition summary; no bulk geometry or tensor payload shall be carried.
4) host_req_valid shall remain asserted until host_req_ready is observed or a local timeout policy aborts the transaction.
5) The response path shall accept host_rsp_valid only when the expected sequence ID and transaction state match. Responses with mismatched sequence IDs, invalid status codes, or expired age shall be rejected and shall not update outputs.
6) A stale_timeout_monitor shall count cycles from request issuance. If the count exceeds timeout_threshold before a valid matching response arrives, the module shall latch timeout and stale_data faults and force safe fallback.
7) A validation_and_safety_filter shall verify response fields and clamp computed actuator commands to the configured min/max range. Any invalid response or out-of-range value shall result in a safe fallback command.
8) An actuator_command_shaper shall produce a deterministic packed command word for active aerodynamic surfaces. The packed command shall support at least target position or deflection command plus optional rate-limit or mode bits. If a floating-point datapath is used internally, it must be synthesized from standard FPGA logic; no special hard macro is required.
9) A safe_fallback_manager shall override all normal commands when fault_out indicates stale, timeout, invalid, or not-armed conditions. Fallback shall be a predefined safe aerodynamic profile selected via register.
10) The module shall expose status for software logging and recovery, including last accepted sequence number, last fault code, and response age.

Implementation constraints:
- The design shall be FPGA-targeted and shall use FPGA BRAM abstractions only if buffering beyond a few registers is needed.
- Do not infer ASIC SRAM macros, generic inferred BRAM for ASIC, or payload FIFOs built from register arrays for bulk storage in an ASIC flow; this module is FPGA-only, so ASIC memory requirements do not apply.
- The RTL shall remain synthesizable and deterministic; all state machines shall have explicit safe states.
- The design shall avoid unbounded combinational paths on host handshakes.
- The design shall include synchronizers if any external asynchronous status inputs are added later.

Interface semantics:
- ctrl_if shall support register read/write for configuration and status.
- host_req_data and host_rsp_data shall be fixed-width packed words carrying only compact descriptors and compact results.
- aero_cmd_out shall be a packed actuator command output with internal saturation.
- fault_out shall encode latched and live fault bits.

Reset, fault, and recovery behavior:
- On rst_n deassertion, clear pending requests, deassert valid outputs, assert safe fallback, and initialize timeout counters.
- Faults shall be latched until clear_faults is written and the system is not in an active fault-triggering condition.
- Recovery from a fault shall require explicit software action; automatic recovery may be allowed only after a valid new request/response cycle.

No surrogate inference claims are permitted in RTL. The host software/GPU side is responsible for executing NVIDIA DoMINO and returning compact results. The RTL is the safety-and-transport wrapper around that external execution.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
NO COMMAND FALLBACK CONTRACT (mandatory; overrides conflicting generated prose): do not create a fallback command, fallback register, fallback status, fallback controller, substitute command, or fallback-on-reset behavior. On invalid, stale, timeout, reset, or fault conditions, inhibit/deassert actuator output validity and latch the fault for software handling. Do not silently replace the requested command.
