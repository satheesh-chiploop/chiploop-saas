The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, fallback, and bounded actuator-command behavior.

EXTERNAL MODEL TRANSPORT DIRECTION CONTRACT (mandatory; this takes precedence over ambiguous ingress/egress wording in upstream prose): the RTL emits model-request valid/data as outputs and receives model-request ready as an input. The RTL receives model-response valid/data as inputs and emits model-response ready as an output. Apply this rule by data flow even when application-specific ports use cmd_*, req_*, rsp_*, or response_* names. A top-level output must have a real RTL driver; never connect a required top-level output only to a child input.
Design a synthesizable FPGA top-level module named adaptive_aero_control_top. The module shall implement a bounded control wrapper around an external NVIDIA DoMINO-based software/GPU surrogate and shall not implement surrogate inference. The top-level interface shall be compact and implementation-friendly: use a 64-bit CSR address/data window and 128-bit valid/ready streaming payloads only. Do not expose geometry arrays, meshes, tensors, or flow fields as individual pins.

Functional requirements:
1) CSR interface:
- cfg_addr[7:0], cfg_wdata[63:0], cfg_rdata[63:0], cfg_we, cfg_re.
- Provide registers for enable, diagnostic mode, request timeout threshold, stale-data threshold, sequence counter seed, actuation min/max bounds, rate-limit enable, fallback mode select, and status clear.
- Implement readable status registers for busy, request_pending, response_pending, timeout, stale, invalid_response, envelope_violation, fallback_active, and last_command_applied.

2) Request path:
- On enable and when not busy, package a request frame into req_data[127:0]. The frame shall contain a request sequence tag, compact flow-condition fields, compact vehicle-state fields, a geometry descriptor ID/pointer, and control flags. The RTL shall not carry raw STL geometry; only a small descriptor or token may be transported.
- Assert req_valid until req_ready is observed. Hold req_data stable while req_valid is high and req_ready is low.
- Latch an outstanding request sequence number and mark request_pending until a matching response is accepted or the operation times out.

3) Response path:
- Accept rsp_data[127:0] only when rsp_valid and rsp_ready handshake occurs.
- Extract compact outputs sufficient to generate active-aero commands, such as drag/lift summary and recommended actuation state. The exact external software/GPU payload definition is not part of RTL; the RTL shall only use the contract fields defined in the register map and response decoder.
- Validate response sequence against the outstanding request.
- Mark stale if response age exceeds the configured threshold or if the response sequence mismatches.
- Mark invalid_response if payload format indicates malformed or unsupported status bits.

4) Safety and fallback:
- On invalid, stale, timeout, envelope violation, or communication loss, drive a deterministic safe fallback command.
- safe_fallback_manager shall support at least two modes: hold-last-safe and predefined-safe-posture.
- Actuator commands shall be clamped to min/max CSR-configured bounds and optionally rate-limited. If the computed command exceeds bounds, output the clipped value and raise envelope_violation or clamp status.
- Output act_cmd_valid only when a command is available and safe to apply; otherwise output the fallback command or deassert valid according to configured mode.

5) Timing and liveness:
- If req_valid is not accepted within the configured timeout window, assert timeout and transition to fallback.
- If rsp_valid does not arrive before the response deadline, assert timeout and transition to fallback.
- After entering fallback, the design shall remain in a safe state until cleared by software or a new valid response is accepted.

6) Implementation constraints:
- FPGA prototype only: use inferred FPGA BRAM or distributed RAM for small queues if required. Do not instantiate Sky130 hard macros in this path.
- Keep storage limited to small control/status registers, a minimal response buffer, and sequence/age counters. No large payload arrays in flip-flops.
- All state machines shall be synchronous to clk and asynchronously or synchronously reset by rst_n according to the selected coding style, with reset driving a safe fallback output.
- Use clear, synthesizable RTL coding patterns: fixed-width arithmetic, enumerated FSM states, registered outputs where needed, and explicit default assignments.

7) Output behavior:
- act_cmd_data[63:0] shall encode the final command bundle for active-aero actuators. Its exact subfield mapping may be defined by firmware/software integration, but it must include at least per-actuator command words or a compressed command vector sufficient for the platform.
- fault_status[15:0] shall encode stale, timeout, invalid_response, clamp, fallback_active, and envelope_violation flags.
- Provide deterministic startup behavior: outputs default to safe fallback until configuration is complete and a valid response is received.

8) Verification hooks:
- Include internal assertions or synthesis-friendly debug flags for request/response sequence tracking, timeout expiration, stale detection, and clamp events if the target flow allows them.
- The design shall be suitable for Arch2RTL translation into synthesizable RTL and for FPGA prototype integration with an external CPU/GPU surrogate service.

Non-goals:
- Do not implement NVIDIA DoMINO inference, mesh processing, or CFD computation in RTL.
- Do not expose model tensors or surface-pressure fields at the top level.
- Do not silently substitute standard-cell register arrays for bulk storage; only small control storage is allowed in RTL.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
