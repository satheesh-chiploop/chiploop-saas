The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, and bounded actuator-command behavior.

Implement a synthesizable FPGA control-and-safety top module named adaptive_aero_control_top. The design shall not instantiate the DoMINO surrogate model in RTL. Instead, it shall implement a compact streaming transport and safety envelope for host-managed surrogate execution.

Functional requirements:
1. Interface:
   - clk and rst_n only for clock/reset.
   - A 128-bit valid/ready input stream for host-to-FPGA requests.
   - A 128-bit valid/ready output stream for FPGA-to-host status and commands.
   - A small CSR window with 32-bit data and 6-bit address for configuration and status.
   - A bounded actuator command output including command-valid, command-value, command-mode, command-fault, and command-safe indicators.
   - Do not expose vehicle geometry arrays, flow fields, pressure maps, or model tensors as top-level ports.

2. Packet format and transport:
   - The input stream shall carry compact request records containing, at minimum: opcode, sequence number, freshness/age metadata, command target, command bounds index, and optional checksum or parity metadata.
   - The output stream shall carry acknowledgments, fault codes, watchdog status, and the final bounded actuator command summary.
   - Packets may be one or more beats long, but the design shall only buffer the minimum control metadata required for safety and sequence tracking.

3. Command validation:
   - On each received request, decode opcode and verify it against an allowed command set.
   - Verify sequence ordering using a stored last_sequence register and reject duplicates or out-of-order commands if configured.
   - Verify freshness/age against a programmable stale threshold.
   - Reject malformed packets, unsupported opcodes, and invalid length indicators.
   - If a response or update is stale, assert a stale-fault and inhibit unsafe outputs.

4. Watchdog and timeout:
   - Implement a programmable watchdog counter started by request acceptance and cleared on valid response acceptance or explicit host heartbeat.
   - If the watchdog expires, assert timeout fault, transition to safe fallback, and suppress normal command propagation until cleared by software or a new valid session.

5. Safety clamping:
   - Command values shall be clamped to programmable minimum and maximum bounds before being forwarded to actuator_cmd.
   - If the command is outside bounds, set a clamp event flag and still forward the clamped value only if all other safety checks pass.
   - If any validation fails, do not forward the command and instead drive the configured safe fallback output.

6. Safe fallback behavior:
   - Safe fallback shall be deterministic and configurable via CSR.
   - Default safe fallback after reset shall be a benign actuator state, such as neutral position or hold-last-valid disabled, per configuration.
   - On fault, the module shall assert cmd_safe and cmd_fault and output the safe fallback value.

7. Storage and synthesis:
   - Use registers for configuration, sequence tracking, watchdog state, fault flags, and one in-flight command shadow only.
   - Do not infer large payload memories, generic SRAMs, BRAMs for model tensors, or flip-flop arrays for bulk geometry storage.
   - For FPGA implementation, if any local buffering is required beyond scalar state, use the platform’s BRAM abstraction only through a vendor-appropriate wrapper; never instantiate a Sky130 hard macro in FPGA synthesis.

8. Reset and initialization:
   - All safety state shall initialize to safe values on reset.
   - Sequence tracking, watchdog, and fault flags shall be cleared or initialized deterministically.

9. Clocking and timing:
   - Single-clock synchronous design preferred.
   - All outputs shall be registered.
   - No combinational loops.
   - No latches.

10. Observability:
   - Provide status registers for current mode, last accepted sequence number, watchdog counter value or coarse status, stale fault, timeout fault, clamp fault, protocol fault, and safe-active state.
   - Provide a clear mechanism for sticky faults if enabled.

11. Host/CPU integration:
   - The software/CPU side is responsible for preparing geometry, invoking the external GPU or NIM surrogate, and packaging the compact response for the FPGA.
   - The RTL shall only implement the transport, buffering, validation, timeout handling, and actuator command gating required by the onboard CPU deployment architecture.

12. Verification-oriented constraints:
   - The implementation shall be deterministic and amenable to formal verification of safety and timeout behavior.
   - Define assertions for: no unsafe command after timeout, no command acceptance when stale, clamp within bounds, and safe fallback on reset.

13. Application context:
   - Domain: automotive aerodynamics.
   - Operating envelope: stream velocity 20 to 55 m/s.
   - Reference conditions may include 38.89 m/s and DrivAerML STL geometry, but these are software/model-side context, not RTL payloads.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
NO COMMAND FALLBACK CONTRACT (mandatory; overrides conflicting generated prose): do not create a fallback command, fallback register, fallback status, fallback controller, substitute command, or fallback-on-reset behavior. On invalid, stale, timeout, reset, or fault conditions, inhibit/deassert actuator output validity and latch the fault for software handling. Do not silently replace the requested command.
