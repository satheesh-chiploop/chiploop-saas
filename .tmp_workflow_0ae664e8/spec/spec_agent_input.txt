The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, fallback, and bounded actuator-command behavior.
Design a synthesizable FPGA digital IP block named adaptive_aero_control_top for an automotive active-aerodynamics controller. The block shall not implement the DoMINO surrogate model; it shall only manage request/response transport, buffering, validation, timeout supervision, safety gating, and actuator command generation.

Top-level interface requirements:
- clk: single system clock.
- rst_n: active-low reset.
- req_valid/req_ready/req_data[127:0]: inbound request stream.
- resp_valid/resp_ready/resp_data[127:0]: outbound status/response stream.
- act_valid/act_ready/act_data[63:0]: outbound actuator command stream.
- service_busy/service_done/service_error: handshake/status inputs from the external software/GPU integration layer.

Packet protocol:
- req_data shall contain at minimum: opcode, transaction sequence number, flow-condition fields including stream velocity, geometry descriptor metadata for STL reference geometry, and control flags.
- resp_data shall contain at minimum: echoed sequence number, acceptance/rejection status, freshness status, timeout status, clamp status, and a compact recommendation/status summary.
- act_data shall contain at minimum: actuator target position(s) or mode bits, a safe-fallback indicator, and clamp status. The exact field widths shall be fixed in the RTL package parameters and remain within 64 bits.

Sequencing and freshness:
- The design shall track one outstanding request transaction at a time unless the implementation parameter enables a shallow in-flight queue of depth 2 implemented with FPGA BRAM or small register state; no unbounded buffering is allowed.
- Every outbound request shall increment a sequence counter. Incoming responses shall be accepted only if the echoed sequence matches the outstanding request and the response arrives before timeout expiration.
- Any response that arrives after timeout, after a newer request, or with mismatched sequence shall be marked stale and shall not drive actuators.

Flow-condition handling:
- The design shall support stream velocity configuration within the operational envelope 20 to 55 m/s.
- The reference operating point shall default to 38.89 m/s and geometry format metadata shall identify STL inputs derived from DrivAerML reference geometry.
- The RTL shall store only compact metadata, not the full vehicle mesh, tensor, or flow-field payload.

Safety logic:
- Clamp logic shall bound all actuator outputs to parameterized minimum/maximum values.
- On reset, service_error, invalid packet decode, stale response, or timeout, the block shall force safe fallback mode.
- Safe fallback mode shall assert a conservative aerodynamic state, such as minimum-risk actuator positions, and shall remain active until a valid, fresh, acknowledged command supersedes it.
- The block shall expose status flags for valid, stale, timeout, clamp, service_error, and fallback_active.

Buffers and storage:
- For FPGA implementation, any bulk request/response buffering shall be mapped to FPGA BRAM or vendor BRAM abstraction suitable for the target toolflow.
- No top-level tensor arrays, geometry arrays, or payload FIFOs implemented as flip-flop banks shall be inferred.
- Small control registers, counters, and FSM state may be implemented in flops.

Control FSM:
- Implement states for IDLE, CAPTURE_REQUEST, ISSUE_SERVICE_REQUEST, WAIT_SERVICE, VALIDATE_RESPONSE, APPLY_CLAMP, OUTPUT_ACTUATOR, SAFE_FALLBACK, and ERROR_HOLD.
- The FSM shall use ready/valid handshakes on all streaming ports and shall not drop accepted transactions without generating a status response.

Timing and throughput:
- The design shall be fully synthesizable and single-clock.
- Backpressure shall be supported on request, response, and actuator streams.
- Latency constraints are implementation-defined; however, timeout counters shall be parameterized and must cover the maximum expected external service latency with margin.

Implementation constraint:
- Because the implementation target is FPGA prototype, do not instantiate Sky130 macros or ASIC-only SRAMs.
- If later retargeted to ASIC, a separate memory-collateral gate shall be required before any hard-macro-based storage mapping.

Parameterization:
- Parameterize timeout cycle count, sequence width, clamp limits, status encoding, and optional queue depth.
- Keep total scalar-equivalent I/O under 256.

Deliverable quality:
- The Arch2RTL output shall include synthesizable RTL modules for packet decode, FSM, freshness checker, clamp block, and safe fallback controller, interconnected by the above streaming protocol.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
