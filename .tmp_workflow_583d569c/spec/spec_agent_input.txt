The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, fallback, and bounded actuator-command behavior.

EXTERNAL MODEL TRANSPORT DIRECTION CONTRACT (mandatory; this takes precedence over ambiguous ingress/egress wording in upstream prose): the RTL emits model-request valid/data as outputs and receives model-request ready as an input. The RTL receives model-response valid/data as inputs and emits model-response ready as an output. Apply this rule by data flow even when application-specific ports use cmd_*, req_*, rsp_*, or response_* names. A top-level output must have a real RTL driver; never connect a required top-level output only to a child input.
Module name: adaptive_aero_control_top.

Purpose: synthesizable FPGA control-plane IP for an intelligent active-aerodynamics controller that interfaces with a CPU/GPU software surrogate service. The RTL shall not implement the physics surrogate, geometry processing, or flow-field generation. Instead, it shall manage compact request/response transport, request validation, stale-data detection, timeout handling, actuator clamping, and safe fallback.

Top-level interface requirements:
1) clk, rst_n.
2) Streaming request interface using req_valid/req_ready and 64-bit req_data.
3) Streaming response interface using rsp_valid/rsp_ready and 64-bit rsp_data.
4) Optional CSR window using csr_addr[7:0], csr_wdata[31:0], csr_rdata[31:0], csr_we, csr_re.
5) Actuator outputs actuator_cmd[15:0], actuator_valid, safe_fallback.

Packetization requirements:
- req_data shall be a fixed 64-bit compact packet containing, at minimum, request sequence, requested stream velocity or velocity delta, mode selector, command enable, and transaction flags.
- rsp_data shall be a fixed 64-bit compact packet containing, at minimum, response sequence, validity bit, stale/timeout indication, fallback indicator, and bounded actuator recommendation summary.
- No top-level tensor, geometry-array, or flow-field signals are permitted.

Control and validation behavior:
- On each accepted request handshake, capture the packet fields into internal registers and increment a local transaction tracker.
- Validate that the requested operating point is within 20-55 m/s when the request contains velocity information.
- Compare incoming sequence/timestamp fields against the last accepted request; mark data stale if sequence is not monotonic, if the age counter exceeds the programmed timeout threshold, or if a response is absent beyond the timeout window.
- Reject requests with illegal opcode, malformed enable bits, or out-of-envelope speed by deasserting req_ready or by setting invalid status and forcing fallback response behavior.
- Maintain sticky status flags for timeout, stale-data rejection, and envelope violation until cleared via CSR.

Actuator control behavior:
- The block shall implement a bounded command generator that maps valid response summaries into actuator_cmd.
- actuator_cmd shall be clamped to CSR-programmed minimum and maximum limits.
- If valid response data is not available, or safe_fallback is asserted, drive the deterministic safe actuator state.
- actuator_valid shall assert only when the output command is freshly updated from a validated request/response transaction.

Timeout and fallback behavior:
- A programmable counter shall start on request acceptance and expire after a CSR-defined number of cycles.
- On timeout, stale response, or invalid packet, safe_fallback shall assert and the output command shall transition to the safe state on the next clock edge.
- The safe state shall be deterministic, synthesizable, and selectable through CSR, defaulting to a conservative low-drag or neutral actuation setting as defined by firmware configuration.

CSR requirements:
- Provide registers for timeout threshold, actuator min/max clamp, operating mode, clear-sticky-faults, status readback, and sequence tracking.
- CSR writes shall take effect synchronously.
- CSR reads shall return current status and control configuration.

Implementation constraints:
- FPGA target: use inference-friendly small registers and optional FPGA BRAM abstraction only for small control buffering if needed; do not instantiate any Sky130 hard macro in the FPGA path.
- The design shall remain below 256 scalar-equivalent top-level I/O count.
- All state machines must be one-hot or encoded in a synthesizable form suitable for FPGA implementation.
- All outputs shall be registered.
- Reset shall place the design in safe fallback, clear transient valid strobes, and initialize clamp limits and timeout counters to safe defaults.

Micro-architecture:
- req_stream_ingress captures req_data when req_valid && req_ready.
- command_precheck checks envelope and format.
- stale_timeout_watchdog monitors timer and sequence age.
- response_latch stores compact response metadata.
- actuator_clamp_fsm computes and bounds actuator_cmd.
- fallback_manager overrides command generation when any fault is active.
- status_regfile stores configuration and sticky faults.

No hardware implementation of the surrogate model is required or permitted in this RTL scope.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
