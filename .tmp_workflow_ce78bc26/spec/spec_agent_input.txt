Implement a synthesizable digital IP subsystem named active_aero_controller_top that supports a transaction-based interface to an external aerodynamic surrogate service and provides safe actuator control. The RTL shall not contain the physics model itself. The design shall be partitioned into the following clocked blocks: (1) geometry_ingress, (2) flow_condition_checker, (3) model_txn_mgr, (4) response_validator, (5) aero_control_policy, (6) command_saturator, (7) safety_supervisor, and (8) fallback_fsm. The IP shall expose synchronous interfaces for input geometry metadata, flow condition metadata, model request/response handshaking, actuator command output, status output, and fault input. All state elements shall reset to a known safe condition on reset_n deassertion.

The geometry_ingress block shall accept a vehicle_geometry_valid strobe and associated geometry metadata fields, including a geometry_format indicator and a geometry_source tag. The block shall only accept geometry_format consistent with STL and shall assert geometry_reject if unsupported format or malformed metadata is detected. The accepted geometry descriptor shall be forwarded to model_txn_mgr and latched only when the input is valid. The flow_condition_checker shall accept stream_velocity_mps and related metadata, compare the velocity against the approved operating envelope of 20 m/s to 55 m/s, and assert flow_valid only when within range. Any value outside the range shall assert envelope_fault and block model request issuance. The block shall also recognize the supplied reference point of 38.89 m/s as a nominal condition but shall not hardcode any performance prediction.

The model_txn_mgr shall generate doMINO_request packets containing a monotonically increasing request_id, geometry descriptor, flow condition descriptor, and a request_timestamp captured from an internal free-running cycle counter or equivalent system timebase. A request may be issued only when geometry_valid, flow_valid, and no active fault or fallback condition is present. The request interface shall include req_valid, req_ready, req_id, and req_payload fields. The response side shall include resp_valid, resp_id, resp_timestamp, and resp_payload fields. Only responses with matching resp_id to the outstanding req_id and with resp_timestamp greater than or equal to the request timestamp shall be considered fresh. Responses failing these checks shall be discarded and shall not affect actuator outputs.

The response_validator shall parse the returned fields drag_force, lift_force, surface_pressure, and flow_field metadata as opaque model outputs suitable for control policy mapping. Because inference results are not available in the supplied evidence, the RTL shall not assume any numerical ranges or predictions for these outputs. The response_validator shall only verify structural validity, freshness, and transaction match. It shall assert model_output_valid only after the response has passed all checks.

The aero_control_policy block shall convert validated model outputs into an intermediate control vector suitable for active aerodynamics actuators. The policy shall be deterministic, synthesizable, and implementation-defined by programmable coefficients or lookup tables. It shall not embed any machine learning inference. The policy shall support at minimum a command vector with one or more actuator channels and a command_enable signal. If model_output_valid is deasserted, the policy shall not emit a new command.

The command_saturator shall clamp each actuator channel to programmable minimum and maximum values. It shall also enforce a programmable rate limit on command changes to prevent abrupt transitions. The command_saturator shall output saturated_command and saturated_valid only when the input command is enabled and the safety supervisor permits release. Any overflow, underflow, or invalid command shall be forced to the nearest safe bound.

The safety_supervisor shall continuously monitor geometry_reject, envelope_fault, response timeout, response mismatch, invalid model outputs, external fault_in, and stale command conditions. A stale command is defined as a command derived from a response that is older than a programmable freshness threshold or that does not correspond to the current outstanding request_id. The supervisor shall assert safe_mode whenever any safety criterion fails. In safe_mode, new model requests shall be inhibited and actuator output shall be driven by fallback_fsm.

The fallback_fsm shall implement a deterministic safe aerodynamic configuration. The exact fallback setpoint values shall be programmable but must be non-learned, bounded, and suitable for a conservative vehicle state. The fallback shall be used when the model path is unavailable, when no fresh response is present, or when the supervisor requests safe_mode. The fallback state shall hold until the supervisor clears the fault and the transaction manager confirms a valid fresh response path is available.

The actuator output path shall select between saturated_command and fallback output using a registered mux controlled by safety_supervisor. The selected actuator_command shall be stable for a full cycle before being released to downstream hardware. The status_telemetry block shall report geometry_accept, flow_valid, request_outstanding, response_fresh, safe_mode, envelope_fault, stale_response, command_clamped, and fallback_active. The design shall also expose fault codes for unsupported geometry, operating-envelope violation, stale response, transaction mismatch, and external fault input.

Timing and reset requirements: all state updates shall be synchronous to clk; all asynchronous inputs shall be synchronized before use; reset_n shall initialize request_id to zero, clear outstanding transaction state, disable actuator output, and assert safe fallback. No combinational path shall allow raw model response data to directly drive actuator outputs. The IP shall be synthesizable for ASIC implementation, use fixed-width registers and counters, and avoid any non-synthesizable constructs. All registers, counters, and comparators required for freshness, monotonic IDs, bounds checking, and fallback selection shall be explicitly described in RTL. The design shall be amenable to Arch2RTL generation as a digital safety wrapper around the external NVIDIA DoMINO Automotive Aero service.
