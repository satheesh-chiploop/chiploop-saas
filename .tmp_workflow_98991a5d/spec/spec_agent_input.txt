The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, fallback, and bounded actuator-command behavior.

EXTERNAL MODEL TRANSPORT DIRECTION CONTRACT (mandatory; this takes precedence over ambiguous ingress/egress wording in upstream prose): the RTL emits model-request valid/data as outputs and receives model-request ready as an input. The RTL receives model-response valid/data as inputs and emits model-response ready as an output. Apply this rule by data flow even when application-specific ports use cmd_*, req_*, rsp_*, or response_* names. A top-level output must have a real RTL driver; never connect a required top-level output only to a child input.
Design a synthesizable FPGA RTL subsystem named adaptive_aero_control_top for an intelligent active-aerodynamics controller. The RTL shall not implement NVIDIA DoMINO inference or any physics solver. Instead, it shall implement transport, buffering of small control metadata, validation, safety enforcement, actuator command handling, and fallback behavior around an external GPU-based surrogate service.

Top-level interface constraints:
1. The top module shall use compact interfaces only. Do not expose vehicle geometry, STL mesh data, pressure fields, flow fields, or surrogate tensors as wide pin arrays.
2. Provide one register-window interface no wider than 64 bits for configuration and status, and streaming request/response interfaces no wider than 128 bits using valid/ready handshakes.
3. Provide an actuator command output interface no wider than 32 bits, also using valid/ready or equivalent handshake.
4. Keep scalar-equivalent I/O below 256 pins.

Functional requirements:
1. The top-level FSM shall include at least the states: IDLE, ISSUE_REQUEST, WAIT_RESPONSE, VALIDATE_RESPONSE, APPLY_COMMAND, FALLBACK, and TIMEOUT.
2. On configuration write, capture mode enable, watchdog limit, freshness limit, command min/max clamp bounds, geometry descriptor ID, and control profile selection.
3. On a request event, package a bounded request record containing: request_tag, geometry_descriptor_id, flow_conditions summary including stream_velocity_mps, profile selector, and any necessary health/status bits. The request packet width shall remain within 128 bits.
4. The design shall increment or otherwise manage a request_tag so that response matching can detect stale, duplicated, or out-of-order messages.
5. The response parser shall accept only packets whose request_tag matches the outstanding request and whose age is within the configured freshness window.
6. If the response is invalid, stale, malformed, or arrives after the timeout limit, assert fault flags and enter FALLBACK.
7. In FALLBACK, drive a deterministic safe aerodynamic command profile selected from configuration or a hardcoded conservative default.
8. Before asserting actuator output, clamp the command to configured safe bounds.
9. The design shall hold the last known good command only if it is explicitly configured to do so; otherwise it shall transition to the deterministic fallback command on fault.
10. The design shall provide status bits for busy, request_pending, response_valid, stale_detected, timeout_detected, clamp_applied, fallback_active, and fault_latched.
11. Reset shall initialize all state to a safe fallback condition with outputs deasserted or set to conservative defaults.

Storage and memory requirements:
1. Because the implementation target is FPGA, any payload buffering shall use the platform BRAM abstraction or small control registers. Do not infer large payload FIFOs as flip-flop arrays.
2. The RTL shall not instantiate any Sky130 hard macros in the FPGA implementation path.
3. If a future ASIC path is derived from this spec, the design must gate any payload storage behind a memory-collateral check and must only use the specified Sky130 SRAM hard macro with required collateral. For this FPGA prototype, that ASIC memory rule is informational only and not to be instantiated.

Timing and safety behavior:
1. The timeout watchdog shall count from request issue to response acceptance and force FALLBACK when the count exceeds the configured limit.
2. The stale-data detector shall compare response age and request_tag against the outstanding transaction context.
3. The command clamper shall be combinational or one-cycle registered, but must not allow out-of-range values to propagate to the actuator output.
4. The design shall never deadlock: when the service is unavailable or late, the FSM must recover to IDLE or FALLBACK and allow a new request after fault handling.
5. The actuator command output shall only be marked valid when the command has passed validation and clamping.

Host/software integration:
1. The host firmware or software is responsible for invoking the external DoMINO service on GPU or remote NIM using the same request semantics as the RTL transport layer.
2. The RTL shall remain agnostic to the physics model internals and shall only consume compact command-relevant outputs.
3. Because inference_status is not_executed in the available evidence, the RTL specification shall not assume any measured surrogate accuracy or latency values.

Implementation notes:
1. Prefer one-hot or encoded FSM as appropriate for FPGA timing closure.
2. Use synchronous clear/reset behavior on all safety-critical registers.
3. Use assertions or equivalent checks in the verification environment to ensure stale packets are rejected, timeout triggers fallback, and clamp limits are enforced.
4. Keep all payload-related metadata bounded and fixed-width.
5. Ensure the architecture can be extended later to a GPU-service adapter without changing the top-level safety contract.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
