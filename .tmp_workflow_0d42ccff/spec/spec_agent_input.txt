The required synthesizable top module is adaptive_aero_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must implement the selected Physical AI application contract, external model request/response transport, validation, safety, timeout, and bounded actuator-command behavior.

EXTERNAL MODEL TRANSPORT DIRECTION CONTRACT (mandatory; this takes precedence over ambiguous ingress/egress wording in upstream prose): the RTL emits model-request valid/data as outputs and receives model-request ready as an input. The RTL receives model-response valid/data as inputs and emits model-response ready as an output. Apply this rule by data flow even when application-specific ports use cmd_*, req_*, rsp_*, or response_* names. A top-level output must have a real RTL driver; never connect a required top-level output only to a child input.

FIRMWARE CONTROL-PLANE CONTRACT (mandatory): this product journey requests generated firmware. The synthesizable top must expose a real firmware-visible CSR/MMIO interface with address, write-data, read-data, transaction-valid/write-enable, and response/ready semantics. DIGITAL_SPEC_JSON.register_contract must describe the implemented registers and fields. Every declared register must be reachable through RTL decode; do not label inaccessible internal state as software-visible. The streaming transport may coexist with, but cannot replace, this interface.
Design a synthesizable FPGA RTL IP block named adaptive_aero_control_top for an intelligent active-aerodynamics controller. The IP shall not implement the NVIDIA DoMINO surrogate itself; it shall implement only request/response transport, validation, freshness monitoring, command buffering, clamp logic, timeout handling, status reporting, and safe fallback control for an external software/GPU surrogate service.

Top-level interface requirements:
1) Use a compact implementation-friendly interface only. Do not expose geometry arrays, tensors, flow fields, or model payloads as wide top-level pins.
2) Provide one 64-bit streaming host command input interface with valid/ready handshake: cmd_valid, cmd_ready, cmd_data[63:0].
3) Provide one 64-bit streaming host response output interface with valid/ready handshake: rsp_valid, rsp_ready, rsp_data[63:0].
4) Provide one actuator output interface no wider than 32 bits per control bundle. The output shall include final sanitized actuator command, mode, valid, fault, fallback, clamp, and sequence echo bits. Internal encoding may be implementation-defined but must be documented in the RTL package parameters.
5) Provide a small register window or parameter port for configuration and diagnostics, limited to 64 bits of address/data visible signaling, without exposing high-dimensional payloads.
6) Include clk and active-low rst_n.

Functional behavior:
1) The controller shall decode command packets carrying: command opcode, sequence number, velocity descriptor, geometry reference/identifier, actuator intent, and any minimal metadata needed for transport.
2) The controller shall verify that operating velocity is within 20 to 55 m/s inclusive. Commands outside this envelope shall be rejected or routed to safe fallback according to configuration.
3) The controller shall validate the packet integrity using a lightweight checksum, parity, or other deterministic integrity field chosen for synthesis simplicity. Invalid packets shall be rejected.
4) The controller shall track freshness using a bounded age counter and monotonically increasing sequence number. Any repeated, out-of-order, or expired command shall be considered stale and rejected.
5) The controller shall buffer a bounded number of outstanding commands and responses using FPGA BRAM abstraction or equivalent vendor BRAM resources for the FPGA prototype. Do not infer large register arrays for bulk payload storage.
6) The controller shall implement a command-state FSM with at least these states: IDLE, RECEIVE, VALIDATE, FORWARD, WAIT_RESPONSE, APPLY, CLAMP, SAFE_FALLBACK, REPORT_STATUS, and ERROR_HOLD. State names may be optimized but the behavior must be preserved.
7) The controller shall support a configurable response timeout. If a response or update does not arrive before timeout expiration, the controller shall assert timeout fault and enter safe fallback.
8) The controller shall clamp all actuator outputs to configured safe bounds before driving the output interface. Clamp logic shall be applied to both absolute command limits and rate-of-change limits if enabled.
9) The controller shall provide a deterministic safe fallback output, such as neutral, hold-last-safe, or predefined safe deflection. The selected fallback mode shall be parameterizable but fixed at synthesis time unless a configuration register permits a bounded runtime choice.
10) The controller shall latch fault reasons including stale-data, invalid-packet, velocity-out-of-range, timeout, and transport-fault. Faults shall be visible on the response/status interface.
11) The controller shall only assert actuator_valid when a packet has passed validation and the output has passed clamping and freshness checks.
12) The controller shall never allow unbounded queue growth. Depths, timeouts, and counters shall be parameterized with safe finite maxima.
13) On reset, the controller shall enter a safe state, clear outstanding command state, clear transient valid strobes, and drive a safe actuator output.
14) The controller shall preserve sequence echo and status bits for observability, but it shall not expose raw surrogate tensors or geometry arrays.

Register/control requirements:
1) Provide small configuration registers for timeout threshold, freshness threshold, actuator min/max bounds, fallback mode, and fault-clear control.
2) Provide read-only status registers for current state, last accepted sequence number, last fault code, clamp flag, fallback-active flag, and timeout-active flag.
3) Writes to configuration registers shall require a valid write enable and shall be ignored during reset.
4) Fault clear shall only be accepted through an explicit control write and shall not clear persistent fault state until the controller is back in a safe idle state.

Implementation constraints:
1) FPGA prototype shall use FPGA BRAM abstraction for buffers and state storage where needed; do not use Sky130 hard macros on FPGA.
2) Do not implement the physics surrogate in RTL.
3) Keep the total top-level scalar-equivalent I/O count below 256.
4) All combinational paths shall be synchronous-friendly and suitable for timing closure on a modest FPGA target.
5) Design shall be fully synthesizable, with no unsynthesizable behavioral constructs.

Safety logic:
1) Stale command rejection shall have priority over normal apply.
2) Timeout shall override normal operation and force safe fallback.
3) Clamp shall happen before actuator output registers update.
4) Any invalid or incomplete packet shall be discarded without updating actuator state.
5) Safe fallback shall be the default when fault status is unresolved.

Documentation requirements for RTL handoff:
1) Document packet field layout, register map, state machine transitions, timeout behavior, clamp limits, and fallback selection.
2) Document that the external surrogate is software/GPU-based and that the RTL only handles transport and safety supervision.
3) Document assumptions about host software providing geometry reference and flow-condition encoding.
4) Document test modes for timeout injection, stale-sequence injection, invalid checksum injection, and clamp-limit violation injection.
FPGA MEMORY CONTRACT (mandatory): describe bulk payload/history/FIFO storage through a technology-neutral memory wrapper that the FPGA flow can map to native block RAM; do not flatten it into registers.
NO COMMAND FALLBACK CONTRACT (mandatory; overrides conflicting generated prose): do not create a fallback command, fallback register, fallback status, fallback controller, substitute command, or fallback-on-reset behavior. On invalid, stale, timeout, reset, or fault conditions, inhibit/deassert actuator output validity and latch the fault for software handling. Do not silently replace the requested command.
