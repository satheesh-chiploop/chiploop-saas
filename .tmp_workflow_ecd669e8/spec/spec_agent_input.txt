Design a synthesizable digital IP block named active_aero_supervisor for ASIC implementation. The block shall not contain the physics/surrogate model; it shall only manage request/response control, validation, safety, and actuator command generation around an external DoMINO service.

1. Top-level function
- The IP shall accept clk, rst_n, control_valid, vehicle_geometry_valid, flow_conditions_valid, stream_velocity_mps, geometry_ref, and optional host configuration inputs.
- The IP shall output model_request_valid, model_request_payload, actuator_cmd_valid, actuator_cmd, safety_status, and telemetry flags.
- The IP shall interface to an external asynchronous model response channel via model_response_valid and model_response_payload.

2. Request manager behavior
- On a qualified control cycle, the IP shall capture a new request ID and sequence number.
- The IP shall package vehicle_geometry reference information and flow_conditions, including stream_velocity_mps, into a model_request_payload.
- The IP shall only issue requests when stream_velocity_mps is within the configured operating envelope of 20 to 55 m/s, inclusive, unless host configuration explicitly routes the system to fallback.
- The request manager shall keep the outstanding request ID, sequence, and request timestamp in registers until a matching response is accepted or the transaction times out.

3. Response acceptance rules
- The IP shall parse model_response_payload fields corresponding to drag_force, lift_force, surface_pressure, and flow_field metadata.
- A response shall be accepted only if response request ID matches the outstanding request ID, response sequence matches the outstanding sequence, and the response age is within a programmable freshness window.
- Any response failing ID, sequence, format, or age checks shall be flagged as stale or invalid and shall not influence actuator_cmd.

4. Command synthesis
- The IP shall contain a deterministic command synthesis unit that maps valid model outputs to actuator command words using local hardware logic or tables.
- The command synthesis unit shall be parameterizable for the target vehicle's active-aerodynamics actuator domain, but shall not implement the surrogate model itself.
- The resulting command shall be a bounded digital word suitable for downstream actuator driver logic.

5. Clamp and saturation
- All synthesized actuator commands shall pass through a clamp unit before output.
- The clamp unit shall enforce a programmable minimum and maximum command value.
- If the synthesized command exceeds limits, the output shall be saturated to the nearest bound and clamp_active shall assert for at least one cycle.

6. Safety supervisor
- The safety supervisor shall monitor request timeout, response validity, envelope compliance, and command bounds.
- On timeout, stale response, malformed payload, out-of-envelope velocity, or internal fault, the supervisor shall inhibit model-derived actuation and enable fallback.
- The supervisor shall assert safety_status bits for stale_reject, timeout_fault, invalid_response, clamp_active, and fallback_active.

7. Safe fallback controller
- The IP shall include a hardwired safe fallback controller that outputs a deterministic safe actuator command when fallback_active is asserted.
- The fallback command shall be configurable at synthesis time or by secure register programming, but must remain within the clamp limits.
- Fallback selection shall have priority over all model-derived commands.

8. Telemetry and observability
- The IP shall expose counters for accepted responses, rejected stale responses, clamp events, timeout events, and fallback activations.
- The IP shall support sticky status bits that remain asserted until cleared by host register write or reset.
- Telemetry logic shall be synthesizable and clocked by clk.

9. Reset behavior
- On rst_n deassertion, all outstanding requests, response flags, counters, and command outputs shall return to a safe known state.
- The default command after reset shall be the safe fallback command.

10. Timing and handshake
- The IP shall use valid/ready handshaking or equivalent internally for request and response channels.
- The design shall ensure no combinational path exists from external model_response inputs directly to actuator_cmd outputs without register or supervisory gating.
- Output actuator_cmd shall be registered.

11. Non-functional constraints
- The RTL shall be synthesizable for ASIC implementation.
- The RTL shall not instantiate GPU logic, neural network layers, or floating-point surrogate inference for the DoMINO model.
- The RTL shall be compatible with a remote NIM or ChipLoop GPU-worker model service accessed only through transaction messages.
- The RTL shall preserve deterministic safety behavior independent of external model availability.

12. Parameterization
- Parameters shall include REQUEST_ID_WIDTH, SEQ_WIDTH, COMMAND_WIDTH, COMMAND_MIN, COMMAND_MAX, FRESHNESS_WINDOW_CYCLES, RESPONSE_TIMEOUT_CYCLES, and SAFE_FALLBACK_COMMAND.
- Parameters shall allow integration with the supplied automotive_aerodynamics application and the reference conditions of stream_velocity_mps = 38.89 and geometry_format = STL with geometry_source = DrivAerML reference geometry.

13. Required status outputs
- stale_reject shall assert when a response is rejected for age or transaction mismatch.
- clamp_active shall assert when command saturation occurs.
- fallback_active shall assert when safe fallback output is selected.
- model_request_valid shall assert only when a request is launched to the external service.

14. Implementation intent
- The block shall be a control-and-supervision IP for active aerodynamics, not a physics solver.
- The block shall be suitable for integration into an automotive ASIC that relies on NVIDIA DoMINO as an external surrogate model service.
