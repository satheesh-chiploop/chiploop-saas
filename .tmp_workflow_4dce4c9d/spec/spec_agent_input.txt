The required synthesizable top module is motor_control_top. Do not substitute a status, telemetry, register-bank, or leaf module as the design top. The top must retain the motor-control request/response, safety, timeout, and actuator-command behavior.
Design a synthesizable ASIC digital IP named doMINO_aeroguard_ctrl that acts as a control-and-safety wrapper around an external NVIDIA DoMINO Automotive Aero service. The RTL shall not implement the surrogate model, numerical solver, geometry processing, or flow-field generation. The RTL shall only manage compact request/response transactions, configuration, validation, timeout, safety clamping, and actuator command delivery.

1. Top-level implementation constraints
- Technology target: ASIC.
- The top-level interface shall be compact and implementation-friendly.
- Do not expose vehicle geometry, surface meshes, STL payloads, flow fields, pressure maps, or surrogate tensors on top-level pins.
- The top-level shall use a 64-bit register-memory window (cfg_bus) and a small valid/ready streaming sideband for request/response and actuator commands.
- Total scalar-equivalent top-level I/O shall remain below 256.
- The design shall be synthesizable in standard digital RTL.
- Any storage used for control/status registers, sequence counters, timestamps, or small descriptors is permitted.
- Bulk payload storage shall not be inferred as flip-flop arrays, reg memories, generic SRAMs, or FIFO register arrays.
- If a future integration requires on-chip payload storage, instantiate only sky130_sram_1kbyte_1rw1r_32x256_8 with ports clk0, csb0, web0, wmask0[3:0], addr0[7:0], din0[31:0], dout0[31:0]. Multiple banks may be used if capacity is required.
- Before any Sky130 payload-memory implementation, require behavioral Verilog, Liberty, LEF, GDS, and SPICE collateral for the macro. If any collateral is missing, stop at the memory-collateral gate and do not substitute standard-cell register storage for bulk payload.

2. Register window
- Implement a 64-bit cfg_bus accessible control/status window.
- The window shall provide at minimum: enable, soft_reset, mode select, timeout threshold, freshness threshold, actuator min clamp, actuator max clamp, sequence number, status flags, and safe-fallback configuration.
- Reads shall return current configuration and status.
- Writes shall update configuration only when allowed by policy and shall not violate safety constraints.
- Invalid writes shall set a fault bit and leave the previous safe configuration intact.

3. Request packaging
- When enabled and not busy, the controller shall create a compact request descriptor containing at minimum a sequence identifier, geometry handle or descriptor reference, flow-condition identifier or descriptor reference, and control flags.
- req_data shall be 64 bits or less.
- req_valid shall assert only when a new transaction is ready.
- req_ready shall gate request launch.
- The module shall not directly serialize large STL data or any model tensor into top-level pins.
- Any upstream geometry delivery shall be represented by compact handles or indices, not by raw mesh expansion.

4. Response handling
- The controller shall accept a compact response descriptor on resp_data when resp_valid is asserted.
- The response shall be validated against the outstanding sequence number and freshness policy.
- If the sequence number does not match the outstanding request, the response shall be rejected and fault/stale status shall be set.
- If the response indicates timeout, malformed status, or protocol violation, the response shall be rejected and the controller shall enter safe fallback.
- The controller shall not assume the presence of full drag/lift/pressure/flow tensors; only compact status and actuator-relevant summary information may be consumed.

5. Safety and fallback
- The design shall implement a staleness guard that compares elapsed cycles or timestamps against a programmable timeout threshold.
- On timeout, stale response, invalid response, or downstream not-ready condition persisting beyond policy, the safe_fallback_controller shall drive a predetermined safe actuator command.
- The safe fallback state shall be deterministic after reset and after any fault entry.
- The controller shall clamp actuator commands to configured min/max values before asserting act_cmd_valid.
- Optional step/rate limiting may be included if configured, but is not required unless it can be implemented without bulk state explosion.
- fault_out shall assert whenever fallback is active, a stale command is rejected, or a protocol/configuration fault occurs.

6. Actuator command generation
- act_cmd_data shall be a compact command word no wider than 32 bits.
- The command output shall be derived from validated compact response summaries and clamp logic, not from raw physics fields.
- The controller shall only forward a command when act_cmd_ready is asserted or when the downstream interface is defined as skid-buffered by a single-entry registered holding stage.
- Command issuance shall be inhibited while busy, while awaiting response, or while a fault is active unless the command corresponds to the safe fallback state.

7. Internal microarchitecture
- Use synchronous FSMs for request issue, response wait, validate, command-apply, and fallback states.
- Use small counters for timeout and age tracking.
- Use small registers for configuration, sequence tracking, and status flags.
- Avoid inferred memories for any bulk data path.
- Keep combinational logic bounded and suitable for synthesis and timing closure.

8. Reset behavior
- On reset, clear outstanding transaction state, clear valid outputs, set safe fallback active, and initialize actuator output to the configured safe default or a hardwired conservative default.
- The design shall not emit a non-safe actuator command until a valid response has been accepted and validated.

9. Clocking and CDC
- The RTL shall assume a single clock domain unless an explicit synchronizer wrapper is added in integration.
- If asynchronous inputs are present, they shall be synchronized before use.

10. Integration behavior
- The wrapper is intended to connect to an external NVIDIA-hosted NIM or ChipLoop GPU worker through system-level transport, but the RTL itself shall only expose compact request/response semantics.
- The design shall support the automotive_aerodynamics use case with reference conditions of stream velocity 38.89 m/s, STL geometry format, and DrivAerML reference geometry as configuration context only.
- The RTL shall not attempt to compute aerodynamics internally.

11. Deliverables for RTL generation
- Produce synthesizable RTL modules: top wrapper, register file, request FSM, response validator, timeout counter, clamp unit, fallback controller, and status aggregator.
- Include assertions for stale-response rejection, clamp enforcement, and fallback entry on timeout.
- Include comments or parameters identifying all safety thresholds and default values for integration.
- Do not include model weights, neural network layers, or physics approximations in RTL.
